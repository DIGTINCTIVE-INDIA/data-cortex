# Job Payload Contract

The request format for submitting a check run, and the responses that come
back. This is the interface between whatever starts a job (the UI backend,
Airflow, `trigger.py`) and the execution engine.

Version 1.0.

---

## Request

```json
{
  "version": "1.0",
  "request_id": "6f1c2a90-3b77-4c52-9a1e-18a2e0f4b7c1",
  "user_id": "f1052957-0aea-4ec1-afc6-3f838ec068b3",
  "checks": [
    { "type": "traditional", "id": "DBC001", "scope": "all" },
    { "type": "traditional", "id": "FBC004",
      "scope": { "fields": { "email": "all", "phone": ["TC005"] } } },
    { "type": "custom", "id": "CB001" }
  ],
  "options": {
    "dry_run": false,
    "continue_on_failure": true
  }
}
```

One object. Nothing is positional.

### Top level

| Field | Required | Notes |
|---|---|---|
| `version` | yes | `"<major>.<minor>"`. Minor = additive, major = breaking. An unknown major is rejected rather than guessed at. |
| `request_id` | yes | Caller-supplied, unique per intended run. The idempotency key -- see below. |
| `user_id` | yes | Must exist in `users`. Every result row is attributed to it. |
| `checks` | yes | At least one item. Order is not significant; items may run in parallel. |
| `options` | no | All keys optional, all defaulted. |

### Check item

| Field | Required | Notes |
|---|---|---|
| `type` | yes | `"traditional"` or `"custom"`. |
| `id` | yes | A single ID string. `DBCnnn`/`FBCnnn` for traditional, `CBnnn` for custom. To run several, repeat the item. |
| `scope` | no | Traditional only. Defaults to `"all"`. Rejected on a custom item -- a custom check is one SQL statement and has nothing to narrow. |

`type` is **per item**, not per job. Mixing families in one request is
supported and routed per item.

One ID per item is deliberate: each item is independently dispatchable, so an
item maps one-to-one onto a parallel task and onto a row in the response.

---

## `scope`

Narrows which of a traditional config's configured checks actually run.
Scope can only ever **subset** what the config already defines -- it cannot
add a check that isn't configured in `traditional_config_details`.

**Everything configured** (the default):

```json
"scope": "all"
```

**Specific fields, all of their checks:**

```json
"scope": { "fields": { "email": "all", "phone": "all" } }
```

**Specific fields, specific checks:**

```json
"scope": { "fields": { "email": ["TC005", "TC007"] } }
```

**Everything except some fields:**

```json
"scope": { "exclude_fields": ["legacy_notes"] }
```

`fields` and `exclude_fields` are mutually exclusive; sending both is a
validation error rather than a silently-resolved precedence rule.

The four mandatory checks (file availability, column names, column order,
datatypes) are config-level, not field-level. **They always run** and are not
affected by `scope`. If they could be skipped, a passing result would no
longer mean the table is the shape the config says it is.

A field named in `scope` that has no rules configured is a validation error,
not a silent no-op -- it almost always means a typo.

## `options`

| Key | Default | Meaning |
|---|---|---|
| `dry_run` | `false` | Validate and resolve the full plan, return what *would* run, execute nothing and write nothing. |
| `continue_on_failure` | `true` | `true`: a failing item doesn't stop the others. `false`: stop dispatching after the first failure. |

`dry_run` exists so the UI can show "this will run 47 checks across 3 configs"
before committing, and so a config can be sanity-checked without writing
result tables.

---

## `request_id` and idempotency

`request_id` is generated by the **caller**, once per intended run, and
resent unchanged on any retry.

The engine records it against the job. A second request carrying a
`request_id` already seen returns the original `job_id` with
`"status": "duplicate"` and starts nothing.

This closes a real hole: today `job_id` is generated server-side, so a UI
timeout followed by the user pressing Run again produces two complete runs
writing to the same output tables, with nothing to detect it.

`request_id` is also what makes per-job staging table names possible for
file-based runs, which is what stops two concurrent jobs on the same file
from overwriting each other.

## Responses

### Accepted

```json
{
  "status": "accepted",
  "job_id": "JOB_6f1c2a90-...",
  "request_id": "6f1c2a90-...",
  "planned": { "configs": 3, "checks": 47 }
}
```

### Duplicate

```json
{
  "status": "duplicate",
  "job_id": "JOB_<the original>",
  "request_id": "6f1c2a90-..."
}
```

### Rejected

Every problem, not just the first -- one round trip should tell the caller
everything that is wrong.

```json
{
  "status": "rejected",
  "request_id": "6f1c2a90-...",
  "errors": [
    { "path": "checks[1].id",
      "code": "NOT_FOUND",
      "message": "Config FBC999 does not exist" },
    { "path": "checks[0].scope.fields.emial",
      "code": "UNKNOWN_FIELD",
      "message": "Field 'emial' has no rules configured on DBC001" }
  ]
}
```

`path` points at the offending location in the submitted document so the UI
can highlight it. Today a rejected payload returns one generic message
pointing at the logs, which the frontend cannot act on.

| Code | Meaning |
|---|---|
| `UNSUPPORTED_VERSION` | `version` major is not recognised |
| `MALFORMED` | Not an object, or a required field is missing |
| `UNKNOWN_FIELD` | Unrecognised key, or a `scope` field with no rules configured |
| `NOT_FOUND` | Config, check or user does not exist |
| `NO_RULES_CONFIGURED` | Config exists but has no field rules -- it cannot run |
| `INVALID_SCOPE` | Both `fields` and `exclude_fields`, or `scope` on a custom item |
| `USER_UNKNOWN` | `user_id` is not in `users` |

### Completion

```json
{
  "job_id": "JOB_6f1c2a90-...",
  "status": "failed",
  "started_at": "2026-10-05T09:14:02Z",
  "finished_at": "2026-10-05T09:16:48Z",
  "items": [
    { "type": "traditional", "id": "DBC001",
      "status": "passed", "checks_run": 24, "checks_failed": 0 },
    { "type": "traditional", "id": "FBC004",
      "status": "failed", "checks_run": 18, "checks_failed": 2 },
    { "type": "custom", "id": "CB001",
      "status": "error", "checks_run": 0, "checks_failed": 0,
      "message": "Source connection DB002 is disabled" }
  ]
}
```

Job `status` is the worst item status: any `error` wins, else any `failed`,
else `passed`.

Per-item status means a caller can tell *which* config failed without parsing
logs -- which is also what makes a partial retry possible.

## Trust boundary

`user_id` is an **assertion, not authentication**. The engine verifies the
user exists; it does not verify the caller is that user.

Authentication is the caller's responsibility. The engine must therefore not
be reachable by anything that has not authenticated -- in practice, the UI
backend is the only caller permitted to set `user_id` freely.

`trigger.py --json` accepts an arbitrary payload from a shell and so inherits
whatever trust the shell has. It is an operator tool, not an API.

## Backward compatibility

The old positional-array form is still accepted:

```json
[
  {"user_id": "..."},
  {"check_type": "traditional", "config_id": "DBC001", "checklist": "default"}
]
```

Shape is detected at the entry point -- a `dict` is v1.0, a `list` is legacy
-- and the legacy form is normalised into v1.0 by a single adapter before
anything else sees it. Nothing downstream handles two shapes.

Mapping:

| Legacy | v1.0 |
|---|---|
| element 0 `user_id` | `user_id` |
| `check_type: "traditional"` | `type: "traditional"` |
| `check_type: "custom_check"` | `type: "custom"` |
| `config_id` / `check_id` / `custom_check_id` | `id` |
| `checklist: "default"` | `scope: "all"` |
| `checklist: {field: "default"}` | `scope: {fields: {field: "all"}}` |
| `checklist: {field: [ids]}` | `scope: {fields: {field: [ids]}}` |
| *(nothing)* | `request_id` generated server-side, with a warning |

A legacy payload gets no idempotency protection, because there is nothing in
it to deduplicate on. That is the main reason to migrate.

Legacy support is removed once nothing sends lists.

## What this changes, and why

| Problem today | Fix |
|---|---|
| `check_type` is required on every item but only the first is used; the rest are silently discarded, so families cannot be mixed | `type` is genuinely per item and routed per item |
| `config_id` / `check_id` / `custom_check_id` -- three names for the thing being run | one `id` |
| Positional array; element 0 is identity by convention only | named top-level fields |
| No version, so any change is a silent break for callers | `version`, checked at the door |
| `job_id` is server-side, so a UI retry runs everything twice | caller-supplied `request_id` |
| Nowhere to put job-level settings | `options` |
| Rejections return one generic message pointing at logs | structured `errors` with `path` and `code` |
| `checklist` carries three shapes and cannot express exclusions | `scope` as a filter object, with `exclude_fields` |
